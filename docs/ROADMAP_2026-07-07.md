# DanceLab Engine Roadmap - 2026-07-07

## Objective

Move the engine from a **working candidate-model backend** to a **validation-ready
decision engine** that covers the most important layers from the PDF and can be
handed back to Claude Code without ambiguity.

## Build Discipline (Project Decision - 2026-07-08)

From this point forward, new engine work should follow a strict `build first,
tune later` rule.

Add new functionality only when it satisfies all of the following:

- it has a clear basis in the PDF, research notes, or credible scientific
  literature
- it can be expressed as an explicit mathematical rule, score, constraint, or
  optimization target rather than only intuition
- it is a natural extension of the current analyzable data we already persist
  or can derive without inventing unsupported latent variables
- it materially improves a real engine decision path:
  analysis -> pair -> next-track -> sequence -> report/API output

Defer for later validation/tuning phases:

- weight fitting, threshold calibration, and confidence-scale tuning
- speculative planner complexity without strong source support
- features that require new labels before they can be honestly evaluated
- open-ended expansion that makes the engine broader but not more usable

Current practical target:

- finish a bounded, usable candidate engine
- keep outputs honest about candidate status
- tune only after the main decision stack is structurally complete

## Priority Order

### Phase 1 - Pair Decision Completion

Priority: `P1`

Status:
completed at candidate level on `2026-07-07`.

Outcome:

- `compatible_contexts` are inferred heuristically in transition windows
- transition strategy classification exists
- unified `EdgeDecision` payload exists and is reused in reports
- pair-level wording stays in candidate / review-required framing

### Phase 2 - Missing Descriptor Coverage

Priority: `P1`

Status:
completed at candidate coverage level on `2026-07-07`.

Outcome:

- `features/microtiming.py` implements syncopation + microtiming profiles
- `descriptors/groove.py`, `bass_salience.py`, `tension.py`, `release.py`
  are wired into `analyze`
- phrase-awareness uses beatgrid anchors plus structural snapping fallback
- `descriptors/breakdown_drop.py` persists `breakdown_likelihood` /
  `drop_likelihood` and refines non-edge segment labels
- mixability and next-track no longer rely on neutral placeholders for the core
  Phase 2 descriptor family

### Phase 3 - Sequence Intelligence

Priority: `P2`

Status:
in progress.

Already added:

- `recommend-next` now accepts recent set history and a requested local arc
- draft `POST /sets/recommend-sequence` beam-searches short continuations
- local arc modes currently supported: `build`, `flat`, `peak`, `closing`
- sequence payload now exposes local/global arc fit plus observed/target energy profiles
- recent-history heuristics now model energy, tempo, and role progression
- sequence planner now applies hard guardrails for cumulative risk, BPM drift, and energy-region plateau
- sequence planner now also scores continuation lookahead and terminal arc reachability from the remaining pool
- sequence planner now carries a bounded set-memory score over recent set-function progression and tension/release history
- shared `rules.py` now powers pair-level hard blocks/penalties across mixability, edge decision, recommend-next, and sequence
- confidence-floor policy now classifies outputs as `allow` / `review_only` / `suppress`
- sequence API horizon supports up to `12`

Goal:
upgrade from pair ranking to set-aware recommendation logic.

Build:

- expose set builder through API
- add sequence / global energy-arc scoring
- extend `recommend-next` so it can use recent set history, not only current track
- support arc modes such as `build`, `flat`, `peak`, `closing`
- add a draft `SequenceDecision` payload

Main files:

- `src/dancelab/decision/set_builder.py`
- `src/dancelab/decision/next_track.py`
- `src/dancelab/api/routes_sets.py`
- new `src/dancelab/decision/sequence.py`

Definition of done:

- the engine can recommend not only the next pair, but also a coherent local set direction
- API can answer both "best next track now" and "best short sequence under this arc"

### Phase 4 - Hard Rules And Guardrails

Priority: `P2`

Status:
in progress at candidate coverage level on `2026-07-07`.

Goal:
turn important DJ constraints into explicit gating logic instead of scattered warnings.

Build:

- shared rule engine with hard blocks / penalties for:
  double-vocal clashes, severe bass overlap, high-risk exposed harmonic clashes,
  unusable BPM jumps
- sequence guardrails for cumulative risk, BPM drift, and energy plateau
- confidence floors for when recommendations should be suppressed or downgraded
- tighter warning taxonomy across decision engines

Main files:

- new `src/dancelab/decision/rules.py`
- `src/dancelab/decision/mixability.py`
- `src/dancelab/decision/next_track.py`
- `src/dancelab/core/provenance.py`

Definition of done:

- recommendations are easier to trust because "unsafe" suggestions are explicitly marked or gated
- pair, next-track, and sequence decisions share one consistent rule layer

### Phase 5 - Validation Readiness

Priority: `P1` ongoing

Goal:
make the engine measurable against DJ annotations instead of only internally coherent.

Build:

- annotation-ready exports for edge and sequence decisions
- benchmark fixtures for transition windows, mixability, context fit, next-track
- validation reports using existing metrics in `validation/`
- calibration review for weights and confidence scales
- practical `validation-pack` artifacts for the active processed corpus

Main files:

- `src/dancelab/validation/`
- `docs/validation.md`
- `docs/test_plan.md`
- `data/examples/`

Definition of done:

- every major decision layer has a clear pilot-ready evaluation path
- future tuning can happen against labeled outcomes, not intuition only

## Recommended Next 3 Tickets

1. Push sequence planning beyond short-horizon beam search only where the next
   step is source-backed and maps cleanly to existing data.
2. Add a crowd-response blocker layer only if it can be defined honestly from
   current descriptors/rules rather than guessed from nonexistent audience data.
3. Start Phase 5 evaluation artifacts so future tuning happens against labels,
   not intuition.

## Success Criteria

We should consider the next roadmap block successful when:

- pair-level outputs stay stable while sequence-level intelligence is added
- recent-history and local-arc context materially change next-track ranking
- unsafe transitions are gated or clearly downgraded instead of only warned
- the engine stays honest about candidate status at every layer
- we stop feature growth once the engine is practically usable and shift further
  changes into validation/tuning work
